# Dispatch Demo 总体设计基线

版本：1.0  
整理日期：2026-09-14（Asia/Shanghai）  
性质：后续剧情系统、数据结构、编辑器和样例实施的总体设计基础。

> **时间范围标记（2026-10-28）**：文中的“七天”是早期体验设想，当前标为“七天（待定，可能延长）”。正式天数要等剧情规模和 Demo 实测后确定。

## 1. Demo 要提供的体验

玩家在一张规模有限、能够逐渐熟悉的小地图中生活七天（待定，可能延长）。玩家通过阅读文本、观察环境、与 NPC 交谈和整理线索，逐渐理解这里的人与事件；随后选择把委托交给谁、告诉对方什么、交付什么准备，并等待选择产生结果。

核心体验不是寻找系统公开的“正确配方”，而是：

- 在有限信息下形成自己的判断；
- 理解不同 NPC 的特点、立场和风险；
- 决定是否继续调查，还是尽早派遣；
- 等待外出 NPC 返回，并观察选择留下的后果；
- 在每天结束时决定自己愿意如何记录已经发生的事。

线索组合承担“发现联系”，派遣承担“作出决定”，返回报告承担“获得不一定完整的信息”，每日撰写承担“表达玩家的判断”。四者共同构成 Demo 的叙事玩法。

## 2. 不采用的设计

Demo 不使用持续流动的游戏内小时和分钟：

- 玩家阅读、探索、思考和停留不会自动消耗日次。
- 不会因为玩家操作慢而错过重要剧情时间窗。
- 白天和夜晚是明确的游戏阶段，通过现有两套天气/表现切换，不是连续钟表模拟。
- 现实中挂机或不刷新游戏不会让当前剧情天数自动过去。

NPC 动作可以有播放时间，委托可以需要若干次换日，但两者都不创建隐藏的分钟成本。

Demo 也不把低收益派遣视为“按钮不可用”。只要 NPC、委托和准备物满足真实操作约束，玩家可以在准备不足或判断不完整时派遣，并承担相应结果。

## 3. 七日结构（天数待定）

当前暂按多日章节设计，早期七天方案仍待定且可能延长。Campaign 统一定义最大日数；DayFlow 负责唯一的日期与阶段事务。

一天由以下阶段构成：

```text
开始当天
  ↓
白天自由活动
  ├─ 阅读信件与地图文本
  ├─ 与 NPC 交谈
  ├─ 收集线索与组合推论
  ├─ 接取、准备和派遣委托
  └─ 听取已经返回的报告
  ↓
玩家请求结束今日活动
  ↓
检查少量必要推进条件，并提示未完成内容
  ↓
进入夜晚撰写
  ├─ 未提交时可以取消并返回白天
  └─ 提交后封存当天记录
  ↓
睡觉
  ↓
处理换日、到期委托和新一天内容
  ↓
下一日或最终收束日（天数待定）
```

在途委托不阻止日终。当天允许结束只检查必要主线条件；可选调查、对话和委托允许未完成，并成为玩家选择的后果。

## 4. 白天自由活动

白天给予玩家充分阅读和思考时间。主要内容来源包括：

- 信件、公告、书籍、物件和环境中的可读内容；
- NPC 对话及对同一事件的不同说法；
- 玩家已经获得的线索和组合出的推论；
- 已开放、已接取、执行中或等待报告的委托；
- NPC 返回后可见的状态变化和新互动。

自由活动不要求按一条固定线性脚本完成。必要教程和主线节点可以顺序推进，可选内容通过独立事件入口开放，不因某条线索未完成而阻塞所有其他互动。

## 5. 线索与推论

线索是玩家已经获知的一条具体信息。它可以来自信件、环境、交谈、委托报告或其他可读内容。

2026-10-23已确认：对话来源的信息随玩家实际听到的内容被动收集；可阅读文本来源的信息由玩家点击指定文本内容主动收集。两类都不以真假或可信程度为收集门槛；获得线索不代表认可其判断，线索匹配仍是建立联系/形成推论。未触达的对话内容不能提前发放。同一线索重复获得不重复授予。此为设计确认，不代表所有正式文本入口已实现；报告回看中的文本与已听取信息如何对应仍需明确。

推论是玩家把若干线索联系起来后得到的调查方向或判断：

- 形成推论不代表系统宣布了客观真相；
- 推论可以不完整，也可以被后续信息修正；
- 推论可以开放新的对话追问、派遣交代或撰写选项；
- 玩家拥有信息，不代表外出的 NPC 自动知道它；必须在派遣准备中明确告知。

世界实际发生的事、NPC 说出的报告、玩家已经知道的内容三者保持分离。这允许误判、遗漏和隐瞒成为叙事内容，而不是数据错误。

## 6. 委托与派遣

基础委托流程为：

```text
委托出现
  → 接取
  → 选择 NPC
  → 选择交付物、证物和告知信息
  → 查看人物反应
  → 确认派遣
  → 跨若干次换日执行
  → NPC 物理返回
  → 等待玩家听取报告
  → 报告信息进入玩家知识
  → 影响对话、线索、撰写和后续剧情
```

派遣的思考来自人物差异、准备差异、信息差异和剩余日数，而不是固定成功率或唯一最优组合。例如，某人擅长追踪但立场偏激；另一人野外能力较弱却更容易取得当地人信任。某件证物交出去可能提高调查效果，也会暂时失去其他用途。

派遣界面可以展示人物已知特点、当前可用状态和作者写的反应，但不能提前暴露隐藏 Outcome、成功概率或把合法选择标成错误。

确认派遣时锁定当时的 NPC、准备物、已告知信息、人物状态、出发日、预计返回日和结果规则。之后修改内容资产或获得新线索，不应无意改变已经发生的出发事实；需要受跨日事件影响的特殊委托必须显式配置。

当前 Demo 的同一委托只能接取并派遣一次；记录本左页仅收录已接取委托，顶部三阶段可点击筛选。早期“条目状态标签只展示”已由后续用户要求更新：可用侧签联动选中并打开对应只读卷宗，待处理入口保持锁定；待听报告仍打开进行中页，不能开始或完成首次报告。确认演变见[记录本记录](ui/PLAYER_NOTEBOOK_UI.md)，实际实现与验收见矩阵。

## 7. 返回、报告与后果

NPC 返回和玩家听取报告是两个不同阶段：

- 返回时可以先释放 NPC 占用，并产生伤势、休息或可见状态变化；
- 玩家尚未听报告时，不提前把报告中的线索和隐藏结果写成已知信息；
- 报告可以取消并重新打开；完成报告时只结算一次；
- 再次查看报告不重复授予物品、线索或剧情结果。

首次听取报告须与已经返回的对应 NPC 对话，进入有表现的听取/提交流程。记录本在进行中分类内显示“待听报告”过渡提示，标签仍打开进行中页面查看已知信息，不提前展示未听取报告、不开始或直接结算首次报告（2026-10-25用户更新）。完成后的只读回看是后续方向，必须引用同一委托实例并与首次事务分开。

重要派遣结果应重新进入玩家所在的小地图或叙事关系中，例如人物状态变化、新对话、信件、物件、线索或其他 NPC 的反应。不是每个结果都需要覆盖所有表现，但至少应留下可辨认的后果。

2026-10-23已确认：派遣报告与NPC对话是获得线索的另一渠道，核心收益是信息，实物不是必需奖励。实际对话中获得的相关描述自动进入线索栏；例如鹿角本体可以没有背包用途，关于鹿角的描述可作为线索。若确实交付实物，则随对话交给玩家进入背包，不要求在报告页另行点击领取。允许只获得线索而不新增背包物品；不因此删除其他物品用途或把所有物品自动转为线索。信息真假仍不影响收集，同一线索重复查看不重复授予。

最后几天若委托来不及返回，必须由数据明确决定：拒绝派遣，或允许作为未决事项进入结局；不能静默消失或伪造提前返回。

## 8. 每日撰写

玩家请求结束白天后进入夜间撰写。每天固定三个撰写部分，每个部分：

- 必须有一个无需条件的默认选项；
- 可以有若干由线索、推论、委托结果、对话选择或其他已知事实开放的选项；
- 玩家只能选择自己当前能够知道或合理表达的内容。

撰写尚未提交时可以取消并返回探索。提交后，当天记录和选择封存，过去日期的线索页只读；随后玩家通过睡觉推进下一日。

撰写不是能力升级或答案评分界面。它表达“玩家知道多少、相信什么、愿意写下什么”，并通过可信度、隐含立场和关键结局标签对长期结局产生影响。

## 9. NPC 在 Demo 中的作用

NPC 首先是玩家判断委托与理解事件的对象：拥有身份、经历、特征、立场、信任和当前身体/可用状态。人物资料、对话内容、运行状态和地图行为必须分离。

未来 NPC 可以在小地图中具有规律活动；玩家熟悉规律后，缺席、受伤或返回才会产生意义。但地图移动、锚点、日程选择和动作 StateTree 是后续表现阶段，不属于当前数据基础阶段，也不应被写进 NPC 资料表。

## 10. 剧情因果与表现职责

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| Campaign / Catalog | 总入口、七日上限、正式内容范围 | 不保存当前游玩状态 |
| Episode / Narrative | 事件、条件、动作、分支、章节出口 | 不复制台词、图片和人物资料 |
| 内容 DA | 信件、对话、委托、线索、推论、人物和 Day 正文 | 不保存本次游玩的变化 |
| 各玩法 Subsystem | 玩家真实获得、派遣、返回、报告、撰写等运行状态 | 不另建一套剧情意义判断 |
| DayFlow | 当前日、阶段、日终与换日事务 | 不与 StateTree 重复推进日期 |
| StateTree / Scene | 开场、教程、转场和场景表现协调 | 不决定玩家选择代表什么结果 |
| UI | 展示正式内容和当前运行状态、发送操作请求 | 不自行结算剧情规则 |

剧情系统应先接收各玩法系统已经提交的真实状态，再根据统一事实选择后续。事件表示“刚发生”，事实表示“现在仍可查询”；玩家晚点打开界面不能因为错过一次信号而永远卡住。

## 11. 制作流程

设计者从一个 Campaign 进入统一 Story Workspace：

1. 在 Content Catalog 创建或选择 NPC、对话、委托、信件、线索、推论和 Day。
2. 在内容资产中填写正文、图片和局部规则。
3. 在 Episode 中编排触发、条件、动作和后续，而不复制正文。
4. 运行跨资产校验，定位重复 ID、错误引用、缺少默认分支和无法继续的流程。
5. 选择正式 DA 启动隔离预览；跳过前置流程，但不使用另一套 C++ 正文。
6. 用可替换样例验证规则，再制作正式多日内容。

具体资产、字段、引用和迁移规则由 [FOUNDATION_DATA_DESIGN.md](FOUNDATION_DATA_DESIGN.md) 定义。本文不重复字段清单。

## 12. 基础联动样例

在正式多日剧本之前，使用一个可替换的小样例验证体验：

- 一份委托；
- 两名具有明确差异的 NPC；
- 两条原始线索和一条推论；
- 若干准备物或可告知信息；
- 两种条件结果和一个默认结果；
- 对应的返回报告；
- 一种返回后可识别的叙事变化；
- 当天三个撰写部分。

未调查时仍可派遣并得到默认结果；调查和推论应能改变派遣判断或结果。玩家完成后应愿意重试另一种选择，而不是只看到测试按钮成功。

## 13. 当前实施优先级

当前优先完成数据基础，不继续扩张 NPC 活动运行时：

1. 统一内容职责、字段、引用和条件语义。
2. 整理旧 DataTable 与正式 DA 的迁移关系。
3. 让派发和其他隔离预览读取正式可编辑 DA。
4. 建立最小数据样本并验证编辑体验。
5. 数据基础稳定后，再依次处理编辑器体验、正式样例和以后所需的场景表现。

## 14. Demo 完成边界

“Demo 系统完成”意味着：设计者能使用正式数据资产建立上述循环，玩家的真实操作能驱动条件与后果，预览和正式流程读取同一内容，并且能诊断某个结果为什么发生。

它不等于：正式多日剧本文案、美术、所有 NPC 日常动作和完整存档自动生成。这些属于在基础系统上持续制作的内容。

本文是当前 Demo 玩法与流程的总体权威说明。历史计划、旧对话总结和示例不得在与本文冲突时重新扩大当前范围；设计变化写入 `DECISIONS.md` 后再更新本文。
