# Dispatch 剧情数据与流程规范：设计及实施计划

日期：2026-09-07

状态：2026-09-08 已实现步骤 1 的数据校验基础及 Episode 独立触发效果、四种重复策略、事件去重和触发诊断。完整事实合同及正式玩法桥接尚未验收，不能视为完整第一批结束。具体见同目录 Dispatch-Step1-Handoff-2026-09-08.md 与 Dispatch-Triggers-Handoff-2026-09-08.md，后者是最新增量。下文未勾选内容仍按各自范围验收。

项目：`F:/Epic Games/Unreal Projects/Dispatch`，Unreal Engine 5.6。

## 1. 最终交付

制作时，从同一个剧情工作区创建和引用人物、委托、线索、推论、对话和日期数据；编辑触发条件、行动及后续分支；直接选择这些 DA 在隔离环境中测试。

运行时，玩家的调查、对话选择、派遣、返回报告和每日撰写真实驱动这些条件。界面、玩法系统与剧情图共享相同内容引用和已发生的事实，避免三处各自判断同一个结果。

验收以可编辑的数据、真实运行结果和可追踪的触发记录为准。完整七天正式剧本文案与地图美术不属于本次交付；测试样例需要明确标注为样例，可替换、可编辑。

## 2. 已经确定的体验约束

- 地图小，游玩有七个日次。
- 没有持续流逝的小时、分钟；阅读、探索、等待与 UI 操作不消耗日次。
- 玩家主动收尾、提交当天撰写并睡觉后才进入下一天。
- 白天、黑夜使用已有天气系统切换。
- 撰写每天三个部分，每部分的可选内容由已发生的行为与已获知的信息提供；保留默认选项。
- 每天只提交一次，提交后封存当天撰写；过去日期的线索页只读。
- 撰写隐藏立场标签，只向玩家显示印记和一句模糊评价，影响结局。
- NPC 在地图中可以活动；活动播放时间与日期推进分开。
- 测试可以跳过接取、对话等前置操作，但读取可编辑 DA；只有运行状态是临时的。
- 沿用已有 UMG 美术。逻辑尽量由 C++ 提供，最终必须交付精确的蓝图控件与绑定修改清单。
- 设计文档保存在仓库外，不向项目添加 docs/superpowers，也不自动提交设计文档。

## 4. 数据职责规范

### 4.1 内容定义、运行状态、规则三者分工

| 数据 | 编辑内容 | 不承担的职责 |
|---|---|---|
| NPC 资料 DA | 身份、职业、肖像、背景、基础特征、初始状态 | 不保存这次游玩的伤势、外出记录、当前移动目标 |
| NPC 活动定义 | 场所、活动步骤、表现任务、适用条件、优先级 | 不再次结算委托，不自行推进日期 |
| NPC 运行状态 | 当前伤势、信任、是否外出、当前活动/派遣实例 | 不覆盖人物资料资产 |
| 委托 DA | 标题图片、委托人、目标、要求、可用条件、准备限制、执行规则 | 不保存玩家是否接取、哪次派遣已结算 |
| 派遣实例 | 唯一实例 ID、委托和 NPC 引用、出发快照、返回日期、进度、结果及领取标记 | 不反向改写委托 DA |
| 对话 DA | 一段对话的节点、选项、条件与效果 | 不要求每句台词创建独立 DA |
| 线索/推论 DA | 内容、来源表现、关联与组合规则 | 不把定义存在等同于玩家已经获得 |
| 日期 DA | 日标题、线索页、三个撰写部分、收尾要求、日终规则 | 不另建小时计时器 |
| 章节/剧情图 | 触发入口、条件、动作、分支与章节出口 | 不复制 NPC 简介、委托文案或 UI 数据 |
| 预览配置 | 引用哪些 DA、初始状态、从哪个入口开始 | 不保存第二套委托/NPC正文 |

跨内容关系以正式 DA 引用为主；稳定 ID 用于保存、查找和诊断；NodeID、OptionID 等局部标识保留。不得要求设计者同时填写指向同一内容的 DA 和另一套旧 DT 行名。

不强制每条规则单独创建 DA。先内嵌在所属委托、对话或章节中；只有确实需要复用的内容才拆成共享资产。

### 4.2 一条剧情规则必须回答的问题

| 字段 | 含义 |
|---|---|
| 规则 ID / 名称 | 稳定定位，日志中能直接打开对应规则 |
| 触发时机 | 开始某日、互动、选择对话、收集线索、完成组合、确认派遣、NPC 返回、听取报告、提交撰写、请求睡觉 |
| 适用范围 | 哪个章节/日次，哪些 NPC、委托或来源；允许不限定某些范围 |
| 条件 | 分组表达“全部满足 / 任一组满足 / 不满足”；支持布尔、枚举/结果 ID、整数比较 |
| 动作 | 发布内容、开始对话、开放委托、切换活动、进入撰写等类型化操作 |
| 完成标准 | 发出请求即完成，还是等待实际完成回执；取消不能冒充完成 |
| 后续 | 条件分支、默认出口、失败出口 |
| 重复策略 | 每次、每天一次、整个流程一次；派遣返回等按实例去重 |
| 优先级 | 决定规则竞争；冲突和相同优先级的处理必须明确且可诊断 |

“事件”表示刚发生的事情；“事实/状态”表示现在可查询的结果。例如“返回事件”可以只通知一次，但“该委托已返回”必须在玩家稍后打开界面时仍可查询，避免错过信号就永远卡住。

主线流程允许顺序推进，同时支持独立的可选事件入口；一个未完成的可选线索不能阻塞当天其他 NPC 互动。等待型节点与立即分支节点在数据上明确区分。

### 4.3 派遣规则

建议状态链：可见 → 已接取 → 准备中 → 执行中 → 已返回待报告 → 报告中 → 已收尾。

准备是可取消的临时草稿。确认派遣时才提交 NPC 占用、交付与实例记录；重复点击不会生成多次派遣。接取状态与 UI 当前选中的委托分别保存。

每份委托设置“需要推进几个日次”。第一日出发、需要两次换日，第三日返回；反复检查同一天不重复推进。在途状态不阻止玩家结束当天。

出发记录至少包括：委托引用、NPC 引用、出发日、预期返回日、实际交付及数量、告知的信息、出发时人物状态、命中规则 ID。默认按出发记录确定结果；跨日事件影响执行结果只允许通过显式规则配置，不读取无关的新状态重新掷一次结果。

结果可以具有调查进展、NPC 后果、交付物去向、返回证据和报告对话。规则判定与结算分别只执行一次；报告可再次查看，不重复奖励。

实际结果与玩家获知的信息分开。NPC 返回可先改变伤势和活动；相应信息在读报告、对话或观察后才成为玩家已知线索，不提前泄露隐藏结果。

物品、情报、证物的交付方式明确：物品移交及消耗/归还；情报告知但保留玩家记录；实体证物可以暂时不可用。对数量和归属做真实事务检查。

准备不足默认仍可派遣，由默认结果处理。不可派遣用于 NPC 外出、委托关闭、交付物不足等实际限制，不能把低收益分支自动当作无效组合。

末日未返回的处理做成委托/流程策略。本版建议允许日终保留“未决”事实并计入结局，界面说明预计返回日；不强行伪造返回。规则必须经过明确验收，不能依靠任务自然消失。

### 4.4 换日与撰写

正式阶段：自由活动 → 请求收尾 → 夜间撰写 → 已提交待睡觉 → 换日处理中 → 下一日自由活动 / 结局。

收尾条件检查发生在撰写前；只设置必要主线要求，可选调查允许未完成。条件未满足时返回准确原因，不能只显示不可用。

未提交时可返回自由活动；提交后锁定当日行为与记录，保证已经封存的线索页和撰写一致。取消撰写不推进日期。

换日顺序：验证已提交 → 防止重复请求 → 确认下一日数据可用 → 更新日次 → 处理到期派遣和 NPC 状态 → 载入当日内容并生成日开始事件 → 恢复玩家控制。发现下一日缺失时，保持原日状态并报告错误。

七日上限由 Campaign 定义，唯一维护；DayFlowManager 负责实际阶段转换。旧根 StateTree 不得再并行推进同一次日期转换。

### 4.5 NPC 活动

活动候选由当前日次、阶段、任务占用、伤势和剧情状态选择。优先级建议：执行/关键剧情占用 > 返回报告 > 受伤休息 > 普通活动。

基础活动只做少量地图锚点之间移动、停留、播放动作、等待互动。活动时间只服务表演；不产生小时和日期成本。

活动执行复用现有 NPC 行为组件与 StateTree/Scene 支持。锚点丢失、移动失败时回到稳定等待状态并记录原因，不能拖死整个剧情。

### 4.6 剧情图、StateTree 与各玩法系统

- 剧情图拥有事件触发、因果分支和后续安排。
- 委托系统拥有派遣实例、返回日期和结算；其结果通知剧情。
- 日期系统拥有当前日与阶段；睡觉是推进请求，不能由多个系统分别累加日期。
- 线索与撰写系统拥有各自收集/提交记录，向剧情提供事实。
- StateTree 执行场景表现与可中断活动，向剧情返回成功、失败、取消。
- UI 读取展示模型和调用正式操作；不重新判定结果、不直接写剧情标签。

## 5. 分步实施及每步验收

阶段按依赖顺序执行；每一步都要有明确可用的结果。实现前细化该步接口和自动化用例；不会先把所有系统同时重写。

### 步骤 1：统一数据合同和条件语义

范围：`NarrativeTypes.h`、`NarrativeRuleEvaluator.*`、`StoryEpisodeDefinition.*`、`StoryCampaignDefinition.*`、`StoryContentCatalog.*`，及领域数据类型。

- [ ] 将第 4 节规范映射为类型化字段，标注哪些沿用、哪些新增、哪些迁移。
- [ ] 为同一规则规定条件分组、缺失值、相同优先级、默认/失败出口和重复触发的处理。
- [ ] 校验实际 DA 类型、引用登记、节点目标、返回天数与日次范围；无效配置不能静默当成 false 或成功。
- [ ] 提供各类条件的可读名称与编辑提示，例如“某委托 / 已返回”“某段对话 / 选项 X”。

验收：在编辑器中配置一个条件分支并得到明确校验；空引用、重复规则、坏分支目标有准确错误位置。先验证数据表达，不要求跑正式第一天。

### 步骤 2：接通 Campaign、剧情事件和实际执行

范围：`StoryDirector.*`、`NarrativeRuntimeSubsystem.*`；新增 `StoryGameplayBridgeComponent.*` 作为连接层。复用现有运行器，不新建第二套剧情图。

- [ ] Director 选择一个 Campaign，统一加载 Catalog、章节和日期定义。配置 Campaign 后，旧 RootStoryTree/旧日期数组不参与另一套独立配置。
- [ ] 收集、组合、对话选择、派遣、返回、报告和提交通过统一入口记录事实；源系统仍拥有自己的真实状态。
- [ ] 绑定剧情动作到正式玩法；异步动作使用请求 ID 回执，失败和取消有明确出口。
- [ ] 支持事实已满足时立即通过，也支持未满足时等待；进入前已经发生的事件不丢失。
- [ ] 提供当前章节、当前节点/活动事件、等待条件、命中分支的调试查询。

验收：真实收集一条线索能改变剧情分支；取消对话不误推进；重新打开界面不会重复触发一次性事件；无效 Campaign 启动不破坏当前会话。

### 步骤 3：实现可配置的派遣生命周期

范围：`CommissionDefinition.*`、`CommissionTypes.h`、`CommissionRuleEvaluator.*`、`CommissionSubsystem.*`、`NPCCommissionComponent.*`，以及现有派发展示模型。

- [ ] 加入执行日数、接取/执行限制与末日策略，沿用正式 DA。
- [ ] 保存出发记录和结果快照，确认派遣做单次事务。
- [ ] 换日检查到期，产生一次返回事件；支持查询等待汇报的实例。
- [ ] 区分物理后果与报告信息；报告取消和重开不重复物品、线索与状态变更。
- [ ] 把结果和准备变更反馈给现有 UI，不暴露隐藏结果为“成功组合”。

验收：同一委托、不同 NPC/交付可走不同规则；第一日出发两次换日后第三日返回；同一日多次检查不提前返回；重复确认/报告不重复扣物品或发奖励；出发后编辑 DA 不改变已有记录。

### 步骤 4：实现日终条件、撰写封存和七日收尾

范围：`DayFlowManager.*`、`StoryRuleTypes.*`、`DailyWritingSubsystem.*`、`WritingDesk.*`、`ABedInteractable.*` 和涉及日期的 StateTree 节点。

- [ ] 添加显式收尾条件、阶段转换和未满足原因查询。
- [ ] 撰写前条件验证，取消可返回，提交只发生一次并封存当天。
- [ ] 睡觉执行一次日次事务，到期派遣先更新，随后产生新一天的内容事件。
- [ ] 缺下一日数据时保持原状态；第七日进入结局，不进入不存在的第八日。
- [ ] 将撰写选项、隐藏立场和评价写入剧情事实，供结局分支使用。

验收：挂机不换日；每次普通交互不扣分钟；未提交不能睡觉推进；在途委托不阻止换日；连续点击睡觉只推进一次；过去线索页不可互动。

### 步骤 5：NPC 资料、状态与活动联动

范围：`NPCDefinition.*`、`NPCInfoComponent.*`、`NPCCommissionComponent.*`、现有 NPC Character/行为/Scene 类；新增独立 NPC 活动定义。

- [ ] 固定资料与当前状态分离，运行 UI 显示真实状态，初始说明只用于预览或背景。
- [ ] 编辑活动锚点、步骤、条件和优先级；从委托和剧情状态选择活动。
- [ ] 接通外出、返回等待、受伤休息和恢复普通活动。
- [ ] 交互/关键剧情可打断普通活动，结束后按照当前状态重新选择活动。

验收：同一 NPC 白天有基础活动，派遣后停止普通活动并离开，返回后出现于约定位置；受伤状态在 UI 和行为中一致；移动失败不阻塞日终。

### 步骤 6：统一编辑、资产迁移与隔离预览

范围：`Source/DispatchEditor/Private/StoryWorkspace/` 及对应 Public、Tests；新增复用现有章节数据的图形编辑组件，不引入第二套保存格式。

- [ ] 内容库显示引用与被引用关系，选中委托可打开人物、结果对话、线索和后续节点。
- [ ] Narrative 页支持节点、连线与条件详情编辑；保存仍写现有 Episode 定义。
- [ ] 显示完整主线与可选入口，以及“为什么触发/为什么没触发”的调试信息。
- [ ] 提供可保存的预览配置，引用用户编辑的 DA；直接设置初始获得线索、可派遣委托、NPC 状态和当前日次。
- [ ] 沿用 L_StoryUIPreview、相同 UI 和正式业务规则；隔离预览创建临时运行会话，不写正式存档或源 DA。
- [ ] 旧 DT/旧节点生成迁移清单并做引用检查；正式入口移到 DA 后才停用旧路径，不删除用户资产。

验收：修改委托图片或台词后再次预览立即可见；无需先接取即可试派遣；可模拟下一日和返回；预览结束不污染正式状态。交付精确的蓝图父类、控件命名、入口绑定和旧节点替换清单。

### 步骤 7：完成一个可替换的联动样例

数据规模：一份委托、两名测试人物、两条原始线索与一条推论、若干准备物、两种结果及对应报告、每日三个撰写部分。测试资产有独立示例目录，不冒充正式剧本。

- [ ] 未调查直接派遣，得到默认结果；先调查并告知信息，得到另一结果。
- [ ] 在地图观察/互动获得线索，组合后开放一条追问或准备选择。
- [ ] 换日后人物返回，真实状态变化；听取报告后获得信息并解锁撰写选项。
