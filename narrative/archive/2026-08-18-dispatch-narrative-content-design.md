# Dispatch 委托、对话、线索、派遣与每日撰写统一设计

日期：2026-08-18  
状态：设计已在对话中确认，等待用户复核本文件  
范围：只定义内容资源、运行时信息流、每日撰写与结局累计，不包含代码或资产制作

## 1. 目标

建立一套容易制作和检查的信息管理方式，让以下系统围绕同一套事实联动：

- 告示牌委托信息；
- NPC 对话；
- NPC 派遣、携带物和返回结果；
- 背包/笔记中的线索；
- 两条线索对照产生的追查方向；
- 每天结束时的三部分撰写；
- 七天结束后的结局选择。

设计必须同时满足：

1. 不把全游戏内容塞进一张大型 DataTable；
2. 不产生“一句话一个 DA”或“一个选项一个 DA”的资产爆炸；
3. 不让 UI 之间直接调用并互相保存状态；
4. 玩家没有获得的信息不能出现在撰写选项中；
5. 撰写只总结已经结束的当天行为，不反向开启新调查；
6. 提交撰写后结束当天、睡觉并进入下一天；
7. 撰写的隐藏倾向只影响最终结局，中途不发能力、装备或数值奖励。

## 2. 不在本次设计范围内

- 不制作自定义可视化对话图编辑器；
- 不支持无限线索组合；
- 不让每次撰写立即生成新的剧情分支；
- 不显示“如实、保守、隐瞒、迎合”等立场标签；
- 不改变旁白 `DT_GuideComments` 的数据形式；
- 不把公共短线索强制改成独立 DataAsset；
- 不在本设计中确定所有正式结局的剧情文本。

## 3. 采用的总体方案

采用“一个委托中心 DA + 少量完整对话 DA + 公共线索表 + 当天 DA 内嵌撰写模板”。

```text
DA_Commission_xxx
├ 委托展示内容
├ 派遣配置
├ 追查方向
├ 结果分支
└ 对话/场景引用

DA_Dialogue_xxx
└ 一次可以独立开始和结束的完整对话

DT_Clues
└ 全局统一格式的短线索定义

DA_DayXX
└ 当天三个撰写部分及其可解锁选项
```

静态资源描述“可能发生什么”；各运行时子系统保存“玩家实际上做了什么”。每日撰写打开时临时汇总运行状态，不额外复制一套事实数据库。

术语统一：本文的“委托”指告示牌发布、可交给 NPC 派遣并产生结果的玩法单位，代码统一使用 `Commission` 命名。玩家收到和收藏的信件继续使用独立 `ULetterDefinition`，不与委托合并；委托结果如需发放信件，只保存对现有信件资产的可选引用。

## 4. 委托中心资产

每个完整委托使用一个 `UCommissionDefinition` 类型的 Primary DataAsset，例如：

```text
DA_Commission_HeartlessDeer
```

### 4.1 基本信息

- `CommissionID`：稳定且唯一的运行时/存档标识；
- 标题、摘要、完整说明、地点；
- 列表图标、详情图片、地图图片；
- 是否允许发布到告示牌；
- 可选的分类或主题标签。

现有 `DT_Quests` 与其引用的 `DT_Documents` 内容迁入这一分类，不再通过 `QuestID -> DocumentID` 拼接展示内容。

### 4.2 派遣配置

- 最大携带槽位，v1 保持当前三个槽位；
- 允许的准备物类型；
- 可派遣 NPC、禁止 NPC、NPC 标签、信任或身体状态条件；
- 默认结果 ID；
- 派遣前的通用预览反应文本。

### 4.3 追查方向

追查方向归属于最适合承接后续玩法的委托资产。它可以引用来自其他委托的公共线索，因此允许少量跨委托对照。

每个追查方向包含：

- `LeadID`，在所属委托内唯一；
- 两个必需 `ClueID`，比较时不区分选择顺序；
- 对照成功后的短旁注；
- 可选的追查说明；
- 解锁后供对话条件和派遣条件读取的稳定标识。

v1 每个追查方向固定使用两条线索；每个核心委托建议只设计 1～3 个有意义的组合。

### 4.4 结果分支

每个结果分支包含：

- `OutcomeID`，在委托内唯一；
- 优先级；
- NPC、携带物、线索、追查方向、世界状态等条件；
- 返回结果等级、标题和摘要；
- 获得/消耗物品；
- 获得线索；
- 命名结果与剧情信号；
- NPC 身体状态或派遣状态变化；
- 可选返程对话 DA；
- 可选后续 NPC 场景引用。

所有条件均不满足时必须存在一个默认结果。返程对话属于表现层：丢失可选返程对话不能撤销已经完成的核心结算。

## 5. NPC 对话资产

一次能够独立开始和结束的完整对话使用一个 `UDialogueDefinition` Primary DataAsset，例如：

```text
DA_Dialogue_Hunter_DeerOffer
DA_Dialogue_Hunter_DeerDispatch
DA_Dialogue_Hunter_DeerReturn
```

不是一句台词一个 DA。一个对话 DA 可以包含十几句台词、多个选项、条件和出口。

### 5.1 对话字段

- `DialogueID`：稳定且唯一；
- `StartNodeID`；
- 节点数组。

每个节点包含：

- `NodeID`；
- 类型：台词、线索暂停、选择、结束；
- `SpeakerID`，UI 从 NPC 信息读取显示名，不在每句话重复填写；
- 多行台词；
- 下一节点；
- 选择项及其条件；
- 结束信号；
- 节点执行效果。

### 5.2 限制效果类型

对话不直接调用线索页、派遣页或撰写页。v1 节点只允许产生少量标准效果：

- `GrantClue`；
- `UnlockLead`；
- `SetStoryTag`；
- `SetNamedResult`；
- `OpenCommission`；
- `FinishDialogue`。

相关子系统处理效果并保存状态，对话 UI 只负责展示和选择。

## 6. 线索与追查方向

公共线索继续使用 `DT_Clues`。Row Name 即稳定 `ClueID`，每行保存：

- 标题；
- 一句简短说明；
- 主题 ID；
- 分类 ID。

线索运行状态由 `ClueSubsystem` 保存，并补充：

- 获得日期；
- 来源 ID；
- 可选的关联委托 ID。

追查方向也由线索系统保存解锁状态和解锁日期，但定义位于所属委托 DA。线索页负责：

1. 查看按日期归档的线索；
2. 选择两条线索进行对照；
3. 查询是否存在策划配置的追查方向；
4. 成功后新增旁注夹页并解锁追查方向。

追查方向可以供 NPC 对话条件或派遣条件读取。撰写不会再产生追查方向。

## 7. 每日撰写模板

每天只提交一次记录。撰写是当天所有事件的最终总结，提交之后睡觉并进入下一天。

为了减少资产数量，撰写模板直接内嵌在已有 `UDayDefinition` 中：

```text
DA_Day03
└ DailyWriting
   ├ Section 1
   ├ Section 2
   └ Section 3
```

v1 固定三个部分。每部分必须选择一个选项。

### 7.1 撰写部分

每个部分包含：

- `SectionID`；
- 标题/提示文字；
- 选项数组。

### 7.2 撰写选项

每个选项包含：

- `OptionID`，在当天内唯一；
- 显示文字；
- 是否为默认选项；
- 解锁条件；
- 内部可信度等级；
- 隐藏立场贡献；
- 可选关键结局 Tag。

解锁条件只使用已经发生的事实：

- 已获得线索；
- 已解锁追查方向；
- 已完成的委托与具体 `OutcomeID`；
- 已存在的 Story Tag；
- 已存在的 Named Result。

未满足条件的选项完全不显示。每部分有且只有一个无条件默认选项，保证任何玩法结果都能够完成撰写。

## 8. 运行时职责

不新增“保存所有东西”的万能数据库。现有系统继续各自保存唯一状态：

### `ClueSubsystem`

- 已获得线索及获得日期/来源；
- 已解锁追查方向及解锁日期。

### `CommissionSubsystem`

- 当前草稿；
- 派遣 NPC 与携带物；
- 委托实例状态；
- 完成结果与完成日期。

### `StoryWorldStateSubsystem`

- Story Tags；
- 数值；
- Named Results；
- 已消耗事件；
- 每日撰写累计的隐藏结局值和关键结局 Tag。

### `DialogueSubsystem`

- 当前对话会话；
- 执行标准效果；
- 不重复持久化线索或委托结果。

### `DailyWritingSubsystem`

- 当前日临时草稿；
- 已提交的每日记录；
- 临时构建撰写上下文；
- 过滤选项、验证提交、计算印记并累计结局数据。

它吸收现有 `QuestSubsystem` 中属于“撰写与提交”的职责；迁移完成后不保留两套并行撰写状态。

## 9. 每日运行流程

```text
开始一天
→ 加载 DA_DayXX
→ StateTree 发布当天事件和委托
→ NPC 对话提供线索/事实
→ 线索对照解锁追查方向
→ 追查方向解锁新询问或派遣路线
→ 派遣 NPC
→ NPC 返回并产生 Outcome、报告、线索和返程对话
→ 当天必要事件全部结束
→ 玩家请求睡觉
→ 打开每日撰写
→ 提交每日记录
→ 播放睡觉过渡
→ 进入下一天
```

打开撰写时，`DailyWritingSubsystem` 临时构建 `WritingContext`：

- 当前天数；
- 已获得线索；
- 已解锁追查方向；
- 已完成委托及 Outcome；
- Story Tags；
- Named Results。

该上下文是即时查询快照，不作为第二份事实数据库保存。

## 10. 提交与存档记录

提交前必须满足：

- 当前日模板有效；
- 三个部分各选择一个当前可见选项；
- 当前日尚未提交。

提交后保存：

```text
SubmittedDailyRecord
├ Day
├ 三个 OptionID
├ CredibilityGrade
├ HiddenEndingContributions
└ KeyEndingTags
```

提交后记录不可修改，不允许重复累计。成功提交发送 `DailyWritingSubmitted` 信号，由 StateTree/DayFlowManager 完成睡觉过渡与下一天切换。

## 11. 可信度印记与模糊评价

每个撰写选项配置一个内部可信度等级：

- `Unformed`：尚未形成判断；
- `Doubtful`：记录存疑；
- `Plausible`：大致可信；
- `Strong`：高度可信。

每日可信度根据三个已选选项的等级取平均并映射到四种印记。玩家只看到印记和通用模糊评价：

- “记录仍缺少足够依据。”
- “其中存在一些尚未解释的矛盾。”
- “这份记录目前基本能够成立。”
- “现有事实对这份记录形成了充分支持。”

印记只表示证据支撑程度，不表示真相对错。

## 12. 隐藏立场与结局

每个撰写选项可以贡献一个隐藏立场：

- `Neutral`；
- `Truthful`；
- `Cautious`；
- `Concealing`；
- `Official`。

这些标签和累计数值不向玩家显示。每日提交时累计到：

```text
Journal.Truthful
Journal.Cautious
Journal.Concealing
Journal.Official
Journal.Credibility
```

只有极少数关键撰写选项设置关键结局 Tag。第七天提交后，`ST_Ending` 根据以下信息选择少量正式结局：

1. 关键结局 Tag；
2. 七天总体可信度；
3. 占比最高的隐藏立场。

本设计不为全部数值组合制作独立结局。

## 13. 编辑器验证规则

### 委托资产

- `CommissionID` 唯一且非空；
- 至少存在一个默认结果；
- `OutcomeID` 与 `LeadID` 不重复；
- 追查方向的两个线索定义均存在；
- 对话与场景引用有效；
- 引用的 Outcome、物品、NPC 和 Story Tag 有效。

### 对话资产

- `DialogueID` 和节点 ID 唯一；
- Start Node 存在；
- 所有下一节点引用有效；
- 至少存在一个从 Start Node 可到达的 Exit Node；
- 每个选择节点至少存在一个默认可用选择；
- 受支持的效果参数完整。

### Day 资产

- 正好三个撰写部分；
- 每部分有且只有一个默认选项；
- 非默认选项至少有一个解锁条件；
- 当天全部 `OptionID` 唯一；
- 可信度和隐藏立场值有效；
- 关键结局 Tag 只用于明确指定的少数选项。

## 14. 运行时容错

- 某部分没有任何条件选项：显示默认选项；
- 默认选项错误缺失：生成“没有足够信息可以记录”的安全选项并报告资产错误；
- 可选返程对话丢失：保留委托核心结算，只跳过对话；
- 必需委托定义无效：不发布该委托并输出包含资产名和字段的错误；
- 对话断链：安全结束对话，不执行断链节点之后的效果；
- 每日三部分未完成：拒绝提交；
- 重复提交：拒绝并保持第一次记录；
- 结局值只在提交成功后一次性累计。

## 15. 验证与测试

至少覆盖：

1. 委托资产的 ID、引用和默认结果验证；
2. 对话节点可达性、断链和默认选择验证；
3. 两条线索顺序互换仍能匹配同一追查方向；
4. 追查方向能解锁指定对话或派遣条件；
5. 不同 NPC/携带物/线索能得到不同 Outcome；
6. Outcome 正确发放线索、结果和返程表现；
7. 每日撰写只显示满足条件与默认选项；
8. 三部分未选满时不能提交；
9. 可信度平均与印记映射正确；
10. 重复提交不会重复累计结局值；
11. 第七天提交后 `ST_Ending` 能读取关键 Tag、总体可信度和主导立场。

## 16. 迁移顺序

迁移期间保留旧 DT 兼容读取，完成引用替换和测试后再删除旧表。

1. 新增委托、对话、每日撰写定义及资产验证；
2. 将 `DT_Quests + DT_Documents + CommissionRulesTable` 合并迁移为委托 DA；
3. 将 `DT_NPCDialogue` 按完整对话会话迁移为对话 DA；
4. 更新委托结果、NPC 组件和 StateTree，使其使用直接资产引用；
5. 将三部分撰写模板迁入现有 `DA_Day01～DA_Day07`；
6. 将追查方向接入线索对照、对话条件和派遣条件；
7. 完成数据迁移检查、引用检查和回归测试；
8. 清除 `DefaultGame.ini` 中废弃或不存在的表引用；
9. 确认无引用后删除相应旧 DT。

继续保留：

- `DT_Clues`；
- `DT_GuideComments`。

## 17. 最终内容制作体验

设计一个新委托时，内容人员只需要：

1. 新建一个委托 DA，填写展示、派遣、追查和结果；
2. 按需要新建少量完整对话 DA，并拖入委托引用；
3. 在 `DT_Clues` 添加该委托用到的短线索；
4. 在对应 `DA_DayXX` 的三个撰写部分添加条件选项；
5. 在 StateTree 中发布委托资产并编排当天流程。

StateTree 只决定“什么时候发生什么”；委托 DA 决定一个委托包含什么；对话 DA 决定 NPC 说什么；运行时子系统记录玩家实际做了什么；Day DA 决定晚上能够如何总结。
