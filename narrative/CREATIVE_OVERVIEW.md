## 一句话概念

当前故事方向为**试验中**。本文件早期提到的“七天”和“五份奇怪的核心委托”是旧剧情草案，不是当前正式剧情数量或时间线。当前记录本中的六个委托仅用于预览和玩法验证，与正式剧情无关；后续剧情会在玩法结构成型后重新设计。

旧草案中的五份委托曾被视为五条核心剧情支柱，但不代表整个 Demo 的任务数量上限。委托数量、核心线、验收者身份、验收目的、完整剧本和结局均待后续设计；当前六个委托资产不应反推这些内容。

可以直接说：

- “我有一个新想法，先记下来。”
- “我想修改某个人物或剧情。”
- “我想增加一种玩法。”
- “我们来写一封信、一段对话或一份报告。”
- “继续看主界面”“优化这个 UI 原型。”
- “这批内容确认了，可以准备录入。”

- “告诉我现在完成了什么。”

## 创作确定度

```text
想法 → 试验中 → 已确认 → 已替代
```

- **想法**：先保存，尚未评估。
- **试验中**：值得继续设计，但可能因可玩性或剧本变化。
- **已确认**：制作目标已确定，未完成时标为“已确认、待实现”，不代表当前实际版本已替换。图片、内容和流程都适用；用户已明确提出同范围修改时直接进入本次迭代，不用为解除旧确认重复请示。验收基线在对应模块完成并满足退出条件后才替换，开发中实际情况即时记录。
- **已替代**：不再采用，保留原因防止旧方案被误当成当前要求。

旧内容若来源或适用性不清，另标“待核对”，不要仅因存在于文档或代码中便视为已确认。具体执行见 [RULES：内容、图片与规则的迭代](RULES.md#内容图片与规则的迭代)；同一张参考图可只保留布局参考、替代其中旧文案，反之亦然。

## 制作进度

```text
草稿 → 待审阅 → 内容已确认 → 已录入 DA
     → 自动验证通过 → 人工验收通过
```

创作确定度和制作进度必须分别记录。“内容已确认”只表示文字和情节可以采用，**不批准资产写入**；正式录入 DataAsset 仍需要单独列出修改范围并获得许可。

## 标准工作流

### 所有既有功能修改的共同入口

先读取对应设计文档的“当前确认”，核对用户要求、确认依据、当前代码/资产的差距；视觉修改先打开当前参考图。用户要求迭代时明确本次拟替代与保留部分，按新目标实施；旧版本用于比较，不是永久限制。缺少现行定义、用户提到旧确认或记录冲突时，按 RULES 的定向回查流程恢复，不推测设计，也不要求每次通读历史或重复确认。实施后逐项报告需求覆盖；对应模块满足退出条件后才更新验收基线和旧版本替代关系，开发中实际情况即时记录，未完成则保留为待实现/部分完成。

当前记录本卷宗：四字段定义见 [NPC 四行信息当前确认](FOUNDATION_DATA_DESIGN.md#npc-four-fields-current)，见闻样式见 [卷宗见闻当前确认](ui/PLAYER_NOTEBOOK_UI.md#observation-layout-current)。这两处保存有效定义；阶段 handoff 保存实施证据，CURRENT 只提供当前停止点。

### 修改剧本

1. 判断这是新想法、试验方向，还是替换当前基线。
2. 检查 Story Bible 的世界真相、人物知识、七日、委托线和揭示关系。
3. 说明连带影响与仍未确定部分。
4. 用户确认后更新 Story Bible；替换既有方向时同步 Decisions。
5. 将受影响的游戏文本标为需要重审。
6. 不自动修改 DataAsset。

### 增加或修改玩法

1. 先描述玩家能做什么，以及它在循环中的输入、反馈和后果。
2. 检查 Gameplay Flow 和现有 `DEMO-*` 要求。
3. 试验想法保留试验状态；成为稳定要求后再更新 Demo Design/Decisions。
4. 只有用户要求实施时，才登记代码子任务、退出条件和验证方式。

### 重新拿出候选想法

1. 开始新的剧情/玩法子任务或遇到具体问题时，先用当前问题匹配 Idea Inbox 的“重新评估触发条件”。
2. 只有触发条件匹配且前置条件已经满足，才重新提出该候选；同时说明它可能解决什么问题。
3. 不因为候选曾被记录就自动采用，也不一次性展示全部旧想法。
4. 候选完成实际验证后，在 Idea Inbox 写明验证证据与结果，并标记为已采纳、修改后继续评估、已搁置或已替代。
5. 被采纳的方向再进入 Gameplay Flow、Story Bible、Text Index 或 Decisions；需要产品实现时另行登记子任务和授权范围。

### 编写游戏文本

1. 从 Story Bible 确认作者或说话者实际知道、误解和隐瞒什么。
2. 确认玩家为何、何时能够看到文本，以及文本承担的揭示或误导作用。
3. 在 Text Index 分配稳定 TextID。
4. 写草稿并由用户审阅；确认后只进入“内容已确认”。

### 正式录入 DataAsset

1. 用户指定要录入的明确批次。
2. 执行者检查 Git、数据设计和现有资产。
3. 先报告拟创建/修改的资产、字段、引用和不包含范围。
4. 用户确认范围后才写入。
5. 执行引用校验、自动验证和正式 DA 预览。
6. 用户人工验收后更新 Text Index 与 Matrix。

### 查询进度

固定回答：当前已确认设计、已实现代码/资产、自动验证、需要重验/人工验收、工作区修改、下一个最小步骤与退出条件。用户不需要指出应读取哪个文件。

## 当前最重要的未决问题

- 正式委托数量与剧情线尚未确定：它们如何组织、是否共同指向一个真相。旧五条核心线仅供历史参考。
- 关联委托如何出现，是否占用 NPC 的派遣时间和每日内容容量。
- 正式 NPC 的数量、身份、动机、能力和秘密如何设计；三个预览 NPC 不预设正式名单。
- 最终收束阶段由谁验收、为什么验收，以及评价事实、立场、服从还是其他目标。
- 教程和收尾之外，需要多少天分配核心内容与可选调查。
- 最短可通关路径、可选调查路径和未完成委托怎样进入结局。

新想法先进入 [Idea Inbox](story/IDEA_INBOX.md)，不需要为了记录灵感提前回答这些问题。
