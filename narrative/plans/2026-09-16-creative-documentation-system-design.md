# Dispatch 创作资料与工作流系统设计

日期：2026-09-16（Asia/Shanghai）  
子任务：`DOC-CREATIVE-001`  
状态：设计稿，等待用户审阅；尚未进入实施。

## 1. 目标

建立一套不要求用户记住文件名、状态口径或制作步骤的本地记录系统。用户只需要用自然语言说“修改剧本”“增加玩法”“写一批游戏文本”“把确认内容录入游戏”或“告诉我当前进度”，当前任务和后续新任务都必须能从统一入口恢复语境、找到权威资料并执行正确流程。

这套系统固定的是资料入口、职责和变更流程，不把尚在思考中的玩法或剧本内容提前定死。

## 2. 当前创作基线

当前故事前提为试验中方向：玩家以囚犯身份来到一个封闭的小型区域，在七天内接触一系列诡异事件和五份奇怪的核心委托；每天结束时把发现、判断与立场写入记录本，第七天有人前来验收记录。

“五份奇怪的委托”是故事承诺和五个核心剧情支柱，不表示整个 Demo 只能存在五个可执行任务。内容可以包含：

- 五条核心委托线；
- 由核心委托产生的前置、调查和后果类关联委托；
- 帮助理解 NPC 的人物委托；
- 不采用正式委托形式的环境调查和可读内容。

验收者身份、验收目的、五条委托的具体内容和完整七日剧本均未定案。它们必须可记录、可讨论，但不能因此成为代码或资产的既定要求。

## 3. 设计原则

1. **用户不负责记路由。** 文件名和更新规则由项目入口与代理说明承担。
2. **少量固定入口。** 初期不为人物、七日、委托线和揭示矩阵分别创建空文档；先集中在一份故事圣经中，内容确实过大时再拆分。
3. **创作确定度与制作进度分开。** “已经想到”不等于“已经确认”，“已经确认”不等于“已经录入游戏”。
4. **玩法、剧本、运行数据各有唯一权威。** 可读总览可以摘要和链接，但不能出现两份互相竞争的正式定义。
5. **背景真相与玩家可见文本分开。** 没有直接展示的历史、人物秘密和因果仍需记录，游戏文本说明玩家如何接触其中一部分。
6. **正式录入需要独立授权。** 用户确认文字内容后，仍要由执行者列出将修改的 DataAsset 和引用范围，获得录入许可后才写资产。
7. **新任务可恢复。** 根 `AGENTS.md` 必须提供创作请求路由；`README.md` 与创作总入口必须说明各文档用途和标准流程。

## 4. 最小文档结构

初期只新增以下固定入口：

```text
docs/narrative/
  CREATIVE_OVERVIEW.md       创作总入口、自然语言路由和全部工作流
  GAMEPLAY_FLOW.md           玩家从开始到第七天怎样游玩
  story/
    STORY_BIBLE.md           故事真相、总纲、七日、人物、委托线和揭示关系
    TEXT_INDEX.md            游戏内文本清单、状态和正式资产映射
    IDEA_INBOX.md            尚未评估的新想法
    texts/                   内容增长后存放具体长文本稿
```

现有制作文档继续保留：

| 文档 | 唯一职责 |
|---|---|
| `DEMO_DESIGN.md` | 稳定的 Demo 设计要求和永久 `DEMO-*` 编号 |
| `FOUNDATION_DATA_DESIGN.md` | DataAsset、字段、引用、校验和迁移规则 |
| `SYSTEM_DESIGN.md` | 当前技术系统与职责边界 |
| `IMPLEMENTATION_MATRIX.md` | 设计、代码、自动验证、人工验收的唯一总体进度 |
| `STATUS.md` | 当前停止点、阻塞和下一步 |
| `DECISIONS.md` | 已采用或被替代的设计决定及原因 |

用户日常只需要知道 `CREATIVE_OVERVIEW.md` 是入口；代理负责根据请求继续读取和更新其他文件。

## 5. 每个新文档的职责

### 5.1 `CREATIVE_OVERVIEW.md`

保持短小，包含：

- 一句话游戏概念和当前创作状态；
- 玩法、剧本、文本、数据、进度分别去哪里；
- 用户常用自然语言请求的路由表；
- 修改剧本、增加玩法、编写文本、正式录入、查询进度的标准流程；
- 创作确定度与制作进度的状态定义；
- 当前最重要的未决问题链接。

### 5.2 `GAMEPLAY_FLOW.md`

面向设计者说明完整可玩流程，而不是实现细节：

- 玩家身份、目标和七天压力；
- 单日循环和第七天收束；
- 探索、NPC、线索/推论、委托/派遣、报告和撰写如何互相反馈；
- 核心委托、关联委托、人物内容和环境调查的区别；
- 不调查、判断错误、来不及返回等不完整状态如何仍然推进；
- 已确认、试验中和待决定的玩法问题。

它是“完整玩法介绍”，但不复制 `DEMO_DESIGN.md` 的详细永久需求，也不记录代码完成度。

### 5.3 `story/STORY_BIBLE.md`

初期在一个文件内设置固定章节：

1. 故事概念与主题；
2. 世界真相与背景历史；
3. Demo 故事总纲；
4. 七日剧情轮廓；
5. 人物、动机、关系、秘密与知识范围；
6. 五条核心委托线及关联内容；
7. 真相、人物认知、玩家获知渠道的揭示矩阵；
8. 结局和第七天验收方向；
9. 尚未决定的问题。

只有内容量已经影响查找时，才把其中章节拆为独立文件，并保持本文件为索引。

### 5.4 `story/TEXT_INDEX.md`

每项计划中的游戏文本使用稳定 `TextID`。清单至少记录：

- 类型：对话、信件、委托、报告、线索、推论、环境文本、撰写或结局；
- 所属人物、委托线和日期；
- 该文本要向玩家揭示或误导什么；
- 草稿位置；
- 创作确定度；
- 制作进度；
- 正式 DataAsset 路径（录入后）；
- 最近一次用户确认记录。

短文本可以暂存于清单；长文本进入 `story/texts/`。运行时正式采用的版本仍以录入后的 DataAsset 为准。

### 5.5 `story/IDEA_INBOX.md`

只负责防止灵感丢失。记录日期、原始想法、可能影响和待回答问题；不因为进入收集箱就成为已确认设计或实施任务。定期整理时，采用的想法移动到玩法或故事权威文档，被放弃的想法保留简短原因。

## 6. 两套独立状态

### 创作确定度

```text
想法 → 试验中 → 已确认 → 已替代
```

- **想法**：仅收集，尚未判断。
- **试验中**：方向有价值，但可能因可玩性或剧本继续变化。
- **已确认**：当前制作基线；以后仍可通过新决定修改。
- **已替代**：不再采用，保留原因避免旧想法复活。

### 制作进度

```text
草稿 → 待审阅 → 内容已确认 → 已录入 DA
     → 自动验证通过 → 人工验收通过
```

两个状态必须分别记录。例如“第七天验收记录本”可以处于创作上的“试验中”，其结局对白处于制作上的“草稿”。

## 7. 自然语言请求路由

根 `AGENTS.md` 和 `CREATIVE_OVERVIEW.md` 应明确以下处理方式：

| 用户说法 | 必须读取 | 默认动作 | 未经授权不得做 |
|---|---|---|---|
| “我有个想法”“先记下来” | 创作总入口、Idea Inbox | 原样保存并标为想法，指出可能影响 | 改权威设计、代码或资产 |
| “修改剧本/人物/背景” | Story Bible、相关文本、Decisions | 核对冲突，提出影响，确认后更新故事权威 | 自动录入 DA |
| “增加/修改玩法” | Gameplay Flow、Demo Design、Matrix | 判断核心循环和 `DEMO-*` 影响，先形成设计 | 直接实施代码 |
| “写对话/信件/报告” | Story Bible、Reveal 章节、Text Index | 分配 TextID、写草稿、记录揭示目的 | 把草稿当正式版本 |
| “这批可以录入” | Text Index、数据设计、Git 状态 | 列出资产和引用范围，等待正式录入批准 | 把内容确认等同资产修改许可 |
| “开始录入/开始实施” | 对应设计、Matrix、Status、Git | 登记子任务并按批准范围执行、验证和交接 | 扩大到相邻功能 |
| “现在进度怎样” | Matrix、Status、最新 handoff、Git | 分开汇报设计、代码、自动验证、人工验收和工作区 | 用单一百分比掩盖未验收项 |

## 8. 标准工作流

### 8.1 修改剧本

1. 先判断这是新想法、试验方向还是要求替换当前基线。
2. 检查 Story Bible 中的世界真相、人物认知、七日轮廓和委托线是否受影响。
3. 列出连带影响和仍未确定部分。
4. 获得用户确认后更新 Story Bible；若替代旧方向，同时更新 Decisions。
5. 检查 Text Index 中哪些文本变为“需要重审”。
6. 不自动修改 DataAsset。

### 8.2 增加或改变玩法

1. 先写入或修订 Gameplay Flow 的玩家流程。
2. 检查它服务哪个核心体验、是否引入新的循环或只增强既有系统。
3. 若成为稳定需求，更新 `DEMO_DESIGN.md` 和永久编号；若没有对应编号，先记 Decisions。
4. 只有用户要求实施时，才在 Matrix 登记代码子任务、明确退出条件并进入技术计划。
5. 玩法试验不能因为写入文档而被误报为已实现。

### 8.3 编写游戏文本

1. 从 Story Bible 确认说话者/作者实际知道什么。
2. 从揭示关系确认玩家为什么、何时能够看到该文本。
3. 在 Text Index 分配稳定 ID，记录用途和揭示目的。
4. 编写草稿并由用户审阅。
5. 用户确认内容后标为“内容已确认”，但不自动录入资产。

### 8.4 正式录入 DataAsset

1. 用户提出或批准录入某一明确批次。
2. 执行者检查 Git、未跟踪文件、数据设计和现有资产。
3. 先报告将创建/修改的资产、字段、引用及不包含范围。
4. 用户确认后才录入。
5. 执行引用校验、构建/自动测试和正式 DA 预览。
6. 用户完成人工验收后，Text Index 标记为人工验收通过。

### 8.5 查询当前进度

回答必须固定分为：

1. 当前已确认的玩法/剧本；
2. 已实现的代码与资产；
3. 自动验证结果；
4. 等待重验和人工验收项；
5. 当前工作区修改；
6. 下一个最小步骤与退出条件。

用户不需要指出应读取哪个文件。

## 9. 新任务恢复顺序

根入口最终应要求所有涉及创作或剧情制作的新任务按以下顺序恢复：

1. `AGENTS.md`；
2. `docs/narrative/README.md`；
3. `docs/narrative/CREATIVE_OVERVIEW.md`；
4. 根据用户自然语言请求，由路由表选择 Gameplay Flow、Story Bible 或 Text Index；
5. 涉及实施或进度时再读 Demo Design、Implementation Matrix、Status 和当前 handoff；
6. 修改前检查 Git 状态、相关差异和未跟踪文件。

入口必须明确：若用户没有说文件名，代理仍负责完成路由，不能要求用户先回忆文档结构。

## 10. 实施范围与退出条件

设计获批后的文档实施包括：

- 创建上述最小入口和模板；
- 把已确认的当前概念填入 Gameplay Flow 与 Story Bible，而不是只创建空文件；
- 在 README 和根 AGENTS 中加入自然语言路由和恢复顺序；
- 在 Decisions 记录“五个固定委托”调整为“五条核心委托线，可有相关内容”；
- 在 Matrix/Status/handoff 中登记和交接本子任务；
- 校验所有本地 Markdown 链接和路由描述一致。

明确不包含：

- 确定五条委托的正式剧情内容；
- 编写完整七日剧本或大量游戏正文；
- 修改 C++、Blueprint、配置或正式 `.uasset`；
- 改变 `DATA-FOUNDATION-001` 已实现的数据合同；
- 自动提交或推送。

主要退出成果是：用户只说常见自然语言请求时，新任务能够从根入口准确找到资料和流程，知道需要读取什么、更新什么、何时需要再次授权，并且不要求用户记住文件名。创作总入口对用户可读是辅助成果，不以用户逐页阅读或记住流程作为验收条件。

## 11. 待用户审阅的问题

本设计推荐把原先计划拆分的 Characters、Seven Day、Commission Arcs 和 Reveal Matrix 先作为 `STORY_BIBLE.md` 内部章节，从而减少需要记忆的文件。只有内容实际变大后才拆分。用户审阅本设计时主要确认这一“先集中、后按需拆分”的方案是否符合使用习惯。
