# 工作与交接规则

2026-09-09，依据用户“保留已有修改、先核对、避免对话中断丢失进度”的要求整理。适用于本系统后续工作；用户最新明确指示优先。

## 开始与恢复

1. 新对话读 CURRENT、本文件及 CREATIVE_OVERVIEW 中当前请求对应的路由/流程，按当前子任务 ID 定位矩阵相关行；涉及设计再读对应设计段落、SYSTEM_DESIGN 或 DECISIONS。同一对话中已读且未变化的规则不反复读。旧 STATUS、handoffs、SOURCES 和 archive 只按需回查，不把整段历史重灌为上下文。
2. 核对当前目录、分支、HEAD、`git status --short`、相关 `git diff` 和未跟踪文件。未跟踪的新源码可能是中断时的重要实现，必须检查。
3. 先确认这次是检查、写文档、修复还是实现。用户只授权检查或要求确认后继续时，不顺手改业务代码。普通“继续”承接当前任务，不能扩大为执行全部历史计划。
4. 已有未提交修改不是垃圾：不 reset、checkout、clean、批量格式化或保存资产来“恢复基线”；不把其他任务的 Widget/美术改动当作本次成果。
5. 找不到关键文件先说明缺失并检查可用证据；不得虚构已完成状态。原始设计待办框和测试预期不是当前进度。

## 确认依据与修改前核对（2026-10-28）

1. 当前任务对应的设计文档维护一处“当前确认”：具体含义、选项/行为、确认来源、替代关系，以及视觉任务的当前参考图。在这一处明确区分“当前已实现版本”和“已确认待实现目标”，不要各建一套重复权威。设计确认不代表实现完成。其他文件链接该段落，不重复维护完整定义。助手建议、用户确认、实施事实分别标记；没有用户确认的数值/映射/权重不能升级为规则。
2. 修改前核对三项：用户当前要求、该处当前确认、实际代码/资产。给用户的工作更新简述关键约束和差距即可，不为已授权工作增加确认关卡。代码缺实现就是缺项，不能修改设计解释来使其看起来已完成。
3. 视觉任务先打开当前参考图，并核对范围：整体样式、行结构、对齐、间距、字体、分隔线、空态和滚动。引用旧图时说明哪些部分仍有效、哪些被后续用户指示替代。用户已要求改版时，以该要求更新目标，旧图用于比较变化；仅缺图、数据变长等输入变化本身不代表已确定新的视觉方向。
4. 用户说“之前确认过”，或文档出现“原字段/原样”但找不到定义、多个有效版本冲突时，按对话ID/回合ID定向读原对话。原助手回复仅为建议/执行记录，确认以用户发言及明确采纳范围为准。记录实际读取范围，不声称自动继承或读过全部历史。无法读取时查本地证据；仍有缺口则只暂停依赖它的更改，并说明缺什么，不猜填。
5. 原对话定位记录在对应设计段落或阶段交接；正常新对话依靠明确的当前确认恢复，无须每次重读原对话。工具返回截断的内容不算已核对完整，须缩小读取范围。

## 内容、图片与规则的迭代

- **均可修改**：设计、文案、参考图、实现和本文规则都可随反馈演进。“已确认”“已验收”及文件名中的 Final/最终仅描述当时版本与范围。用户最新明确要求是本次改动依据；同范围已授权修改直接进行，旧确认不能成为重复请示或拒绝迭代的理由。一般性“都能迭代”也不等于授权重做全项目或写入正式DA。
- **先确定本次变化**：在对应设计段落或同阶段交接中简记修改对象、原因、旧→新差异、保留部分、来源及日期；局部改字/间距不必另立版本文件或设计计划。新方案还在试验时，与现行方案明确区分；用户确认采用后记为“已确认、待实现”，只更新目标。内容、视觉可分别迭代，不要求同步整套重做。
- **完成后才替换验收基线**：在同一现行段落分别记录“上次验收版本（没有证据就写未建立）”“当前工作区实际情况”“已确认待实现目标”。开发中的源码、资产、已加载程序可能不同，发生修改立即更新实际情况；完成前不把新方案升级为验收基线，也不把已被改动的工作区描述成完整旧版。对应模块或明确限定的子范围满足退出条件及所需验证/人工验收后，才更新验收基线和旧版本替代关系。部分实施写部分完成；验证未过写待验证；局部完成不代表父级或全项目完成。
- **状态明确**：沿用“想法/试验中/已确认/已替代”的创作状态；证据不足的旧条目另标“待核对”，不自动升格为现行要求。“已确认”与实现、测试、人工验收仍分开；日期较新或已在代码里都不能单独证明设计已采用。
- **图文分项替代**：图片记录路径、日期或版本、用途（风格参考/布局参考/实际渲染）、有效区域和被替代部分。旧图中的文案、NPC、物品、颜色、布局可以分别过期；不能凭一张图冻结全部内容。文本记录对应条目/TextID、正文或唯一来源、修改范围；改正文不自动改配图/排版，改图也不自动覆盖正文。
- **同步改入口和依据**：方案确认时在所属设计/文本索引更新目标和待办；重要设计转向写DECISIONS，微调复用当前交接。模块完成后更新实际版本，旧实现段落标“已替代”并链接新版本及完成证据；旧设计目标若提前撤销，注明“目标已替代，实现尚未替换”。CURRENT及矩阵分别同步目标、实施、验证、人工验收，不能一次全部改成完成。历史图片/证据需要保留时使用不同文件名或备份，不能覆盖后仍称为旧版证据；不得因此擅自删除资产。
- **按影响重验**：变更需求或验收标准后，旧证据即使对应同一代码，也不能自动证明新要求。受影响项标“需重新核对/需要重验”，选用新文本、新图片及真实输入验证；不相关的已有结果继续保留。纯文档措辞澄清不自动触发全项目重测。
- **旧内容随任务清理**：每次读取相关段落时检查其来源、适用范围、替代链接与当前事实。确认过期则更新现行摘要、标记旧段落或移入历史；暂时无法判断则标出具体疑点，只在影响本次决策时追查。只报告实际核对范围，不宣称所有旧文档已清理；全库整理需作为明确任务，避免每次工作先通读全库。

## 系统实现约束

- 遵守 SYSTEM_DESIGN 的职责边界；复用现有 Runtime、Catalog、Episode、Subsystem 和 Widget，不建第二套剧情图、日期、撰写或测试业务逻辑。
- 正式 DA 引用为主，ID 用于稳定查找和局部结果；不能让设计者同时维护同一内容的 DA 与旧 DT 行名。
- 源系统先提交真实状态再发事件；同一事项保留稳定身份，处理重入、重复、失败和取消。快照不重放奖励，动作回执不能早于依赖事实。
- 清理仅关闭本请求拥有的对象/会话。异步回调要核对身份，不能仅以同一个 NPC/书桌等目标判断会话归属。
- 旧 DT、接口、蓝图、地图的删除必须先有引用审计和迁移验收，并获得相应授权；旧计划里出现删除/提交命令不等于当前授权。
- 不改现有 UMG 美术来规避逻辑问题。需要用户调整蓝图时列明父类、控件名、事件/绑定和旧节点替换。
- 预览只使用隔离会话状态与正式业务 API；不修改正式存档、源 DA、Widget 默认对象或当前用户关卡来注入测试数据。

## 验证与报告

1. 功能/修复用相关实际行为测试；测试对象按 UE 要求构造，GameInstanceSubsystem 必须有 GameInstance 外层。把夹具失败、业务失败与环境失败分开。
2. 每阶段执行适当的 DispatchEditor 构建和相关自动化。仅文档变更检查实际内容、链接和变更范围；本轮复制/归档证据时再校验哈希，不为普通文字修改要求全套归档或游戏测试。
3. 保存准确命令、配置（Development/DebugGame）、过滤器、通过/失败数、进程结果和日志路径；统计 Test Completed，不以“进程退出”代替测试通过。证据注明日期、HEAD及相关未提交文件的差异快照或哈希、使用的资产/输入与实际加载配置；旧记录无法对应时标“历史通过，版本对应关系待核对”，不能反推当前通过或当前失败。
4. 记录失败，即使其他组通过也不能说全部通过。修复后只重跑覆盖修复所需的测试，有新风险再扩大范围。
5. 区分设计目标、代码已写、测试通过、人工验收。手动 CompleteAction 的纯逻辑测试不能证明真实 UI/场景动作已接通。
6. 沙箱阻止构建/缓存时使用正常权限流程；不修改引擎脚本绕锁，不终止其他任务进程。自己启动的进程要记录身份与结束状态。
7. 本地 docs 不自动强制加入 Git、不自动提交/推送。源码与资产是否提交遵循当前用户授权。

8. 验收必须逐项映射用户要求与证据覆盖范围。构建成功只证明相应配置能编译；静态检查不证明运行效果；数据读取通过不证明视觉符合参考。新增长正文、缺图、不同分辨率等实际输入必须针对剩余风险验证，不能继承短示例的完整显示结论。
9. 视觉修改须对照当前目标参考与本轮实际渲染图，报告具体差异和仍未验收部分。设计图不能充当已实现截图；新渲染图也须核对加载版本和验收范围。测试必须能区分被否决方案与正确需求，不能只断言本次实现选择。记录宿主实际加载配置、发现的测试名和截图输入；未匹配到测试不能算通过。
10. 用户否决方案后，原通过结果降为“仅证明被否决方案”；撤回源码后明确是否已编译/加载，不能宣称运行页面恢复。环境故障、代码错误及用户否决分别记录，不把沙箱权限失败直接解释为用户电脑权限损坏。

## 持续记录，避免再次依赖长对话

- **完成一个可验证小步骤后检查 CURRENT 与矩阵相关行**：停止点、范围、阻塞、验证或下一步有变化就立即同步相关字段，未变化的行不重写。CURRENT 只写短摘要和证据链接，不重复过程日志；不要为每次读取、命令或普通回复新建交接。
- **方案改变或用户纠正范围时立即更新**：CURRENT 更新下一步与授权边界；只有采用/替代设计路线时更新 DECISIONS。尺寸、颜色、措辞等既定方案内的微调写当前阶段交接即可。
- **开始耗时构建/测试前记录**：正在执行的命令、日志、任务/进程标识（若可用）。返回后写实际结果，不留下“正在运行”假状态。
- **出现失败/阻塞时立即记录**：错误摘要、已尝试事项、是否改了文件、下一次最小诊断，不只写“继续处理”。
- **阶段交付、主动停止或预计上下文不足时更新 handoff**：用 HANDOFF_TEMPLATE，同阶段小幅修正复用当前文件，阶段切换或重要设计转向才新建；保留先前失败、结果与替代原因，不改写成一直成功。检查下一位仅凭文档能定位代码与日志，不等待自动压缩成功再写。
- CURRENT 只保留当前可操作摘要，长期记录追加到 `handoffs/`；旧 STATUS 原文保留为历史时间线、不再逐轮追加。已解决项标明证据，不简单删除失败历史。归档原文不回写。
- 不需要再读完所有历史：每次从 CURRENT 读最新摘要，再按 ID/证据链接检查矩阵、代码和必要原文。文档变更日期不等于内容已实现日期。

## 总设计与子任务同步

### 当前入口与纠错维护

- CURRENT 只保留一份有效快照：当前目标、确认依据链接、四类状态、具体差距/阻塞、下一步与证据入口。状态变化更新对应字段；不把每轮过程不断追加为多个“当前”。保留必要历史时移入对应阶段交接或带日期的历史归档。
- 发现错误或过期结论，在原位置写明“已纠正/已替代/历史证据”和替代链接；更新当前入口及矩阵相关行。不能只在末尾追加反驳，让原错误仍显示为有效事实。历史失败/原文留存，不删除证据来伪造一直成功。
- 阶段交接必须指出确认依据、未实现项和每项证据的边界。未实现但设计已确认的内容写“设计确认，待实现”，禁止用“保留原字段”等含糊摘要隐藏缺项。
- 每次交接做一次恢复检查：下一位不打开长历史，能否定位当前实际版本、已确认目标、各自图文依据、实现差距和第一个可执行动作？不能定位就先修交接，不靠增加同义总结补救。

- `DEMO_DESIGN.md` 使用永久 `DEMO-*` 编号定义总要求；`IMPLEMENTATION_MATRIX.md` 是唯一总体进度表。
- 每个子任务必须有稳定 ID，并在矩阵登记父级编号、明确范围、明确不包含项、状态和最新交接。没有登记不得开始剧情业务修改。
- 每次可验证进展核对矩阵相关行与 CURRENT，同步有变化的字段；详细证据只写阶段 handoff，其他位置引用它。阶段结束 handoff 必须包含子任务 ID、父级编号和四类状态变化。
- 设计确认、代码实现、自动验证和人工验收不得合并成一个“完成”。子任务只能更新自身证据覆盖的列。
- 新要求若没有父级编号，先更新 DEMO_DESIGN 和 DECISIONS，再建立子任务；不能让新对话创建脱离总体设计的孤立功能。
- 新对话发现矩阵过期时，以用户最新指示和本地证据纠正矩阵，并记录纠正原因；不能因为旧子任务写了“完成”就沿用错误结论。

## 防止原地踏步的执行门槛

- **限制在制品**：默认只能有一个主要实施子任务标记为“进行中”。新想法先进入矩阵等待队列；用户明确要求并行时，也只能并行互不依赖且不修改同一批文件/资产的任务。
- **开工条件**：子任务开始前必须具备父级 `DEMO-*` 编号、明确范围与不包含项、所需输入、现状证据和可执行的第一步；缺少关键用户选择时不得假装开工。
- **退出条件**：子任务必须提前限定本次可验收范围，例如“维拉三条见闻展示”，不能笼统用“整个记录本”作为一次微调的完成范围；写清用户能观察到的行为及设计、代码、自动验证和人工验收各自需要什么。退出条件未全部满足时只能写“部分完成”或“等待验收”。
- **验证新鲜度**：测试证据记录日期和对应工作区/HEAD。源码、资产、配置或测试环境变化可能影响已通过项时，立即改为“需要重验”；重新运行成功后才能恢复 GREEN。仅改文档、提交既有文件或修改提交标题，不会自动使相同输入上的测试失效；核对相关文件与环境是否变化，不以 HEAD 变化本身要求全量重跑。无法确认对应关系时明确标注“证据对应关系待核对”，不能推定当前通过。
- **可观察成果**：每个阶段至少交付一个用户能直接检查的结果，例如可创建的正式 DA、可编辑字段、可读校验错误、能用正式 DA 启动的预览，或明确的 UI/PIE 行为。只有内部类、接口和自动化测试不构成阶段完成。
- **进入下一阶段**：先完成当前子任务退出检查、更新矩阵/CURRENT/handoff，再开始下一个主要子任务。若选择带着缺口前进，必须由用户确认，并把缺口登记为阻塞或明确后续任务。

### 图文迭代与收尾的更替检查

这是执行条件，不等用户发现过期内容后才排查。每个可验证小步骤仍按上文即时更新；用户确认效果、阶段收尾、转入下一任务或准备交接前，再检查本次受影响的现行段落：

1. **当前入口原位更替**：设计文档“当前确认”的主图/正文/字段定义指向实际新版本；不能仅在文末追加“最新进展”而让主入口保留旧版本。新图保存到稳定证据目录，记录来源、日期、用途和替代范围；旧图保留但在旧引用原位置注明历史及替代入口，不覆盖旧证据文件冒充原记录。
2. **状态一致**：设计目标、当前工作区、自动验证、人工验收分别核对。收到用户“可以了”等明确确认时，只更新其确认范围，不继续写该范围“待复看”，也不扩大为未展示模块或父级整体验收；无确认时不擅自升级基线。
3. **检查本轮旧表述**：对本次变化列出简短替代表（如空图→已接图、旧日→新日、旧报告段落→新段落）。在当前设计、CURRENT、矩阵有效快照及登记行、交接当前停止点逐处核对；文本有变化再查TEXT_INDEX/批次。只查本轮范围，不要求全库重审。历史中的同词可保留，但必须看得出历史身份。
4. **检查图片和链接**：实际打开新图；确认当前主链接可达且文件内容正确。复制的用户图/验证图核对哈希。链接存在不等于内容已更替，自动扫描不代替正文和画面核对。
