# Dispatch 项目协作入口

进行剧情、StateTree、委托、对话、线索、撰写、NPC 或 Story Workspace 相关工作前，先从当前交接入口恢复，不默认通读历史：

1. `docs/narrative/CURRENT.md`（当前停止点、四类状态、下一步和证据入口）。
2. `docs/narrative/RULES.md`（安全边界与交接规则）；从 `docs/narrative/CREATIVE_OVERVIEW.md` 读取当前请求对应的路由与流程。新对话重新建立上下文；同一对话中已经读过且未变化的规则不逐轮重复读取。
3. 从 `docs/narrative/IMPLEMENTATION_MATRIX.md` 只读取当前快照、相关子任务与父级 `DEMO-*` 行；它仍是唯一总进度映射。新任务或设计变化再查 `docs/narrative/DEMO_DESIGN.md` 的相关编号与设计段落。
4. 当前任务涉及玩法时读 `docs/narrative/GAMEPLAY_FLOW.md`；涉及剧本、人物、背景、七日或委托线时读 `docs/narrative/story/STORY_BIBLE.md`；涉及对话、信件、报告等游戏文本时读 `docs/narrative/story/TEXT_INDEX.md`；只要求记录新想法时读 `docs/narrative/story/IDEA_INBOX.md`。
5. 当前任务涉及数据时读 `docs/narrative/FOUNDATION_DATA_DESIGN.md`；涉及技术设计时读 `docs/narrative/SYSTEM_DESIGN.md`、`docs/narrative/DECISIONS.md`；需要旧路线、原始细节或证据时，按 `docs/narrative/README.md`、`STATUS.md`、`SOURCES.md` 与交接链接定位相关部分，不把历史全文当作默认必读。

用户不需要记住上述文件名。即使用户只说“修改剧本”“增加玩法”“写/录入文本”“记录想法”或“查询进度”，当前任务也必须按 `CREATIVE_OVERVIEW.md` 的自然语言路由自行读取和更新正确资料，不能要求用户先指定文档。内容确认不等于资产写入许可；正式修改 DataAsset 前必须再次列出资产、字段、引用和不包含范围并获得授权。

设计新的剧情/玩法子任务，或当前问题涉及内容重复、反馈不足、经济缺少用途、日期缺少变化、地图/功能扩展、结局输入等主题时，必须检查 `docs/narrative/story/IDEA_INBOX.md` 的“重新评估触发条件”。只重新提出与当前问题匹配且前置条件满足的候选，并说明它解决什么问题；不能一次翻出全部旧想法，也不能把候选自动升级为需求。实际验证后必须回写验证结果和处理状态。

这些文档是项目本地交接记录。`CURRENT.md` 是入口而非独立权威；若它与矩阵、代码或用户最新指示冲突，先核对并修正，不能把旧任务标题或历史计划的勾选状态当作当前事实。若文件缺失，说明缺失情况，并先核对代码、Git 与用户指示。

修改既有功能前必须读取对应设计文档的“当前确认”段落；视觉任务必须打开其中指定的当前参考图。确认依据、当前实现和验证范围分别核对，不能用已有代码或测试通过反推用户设计。不得把“保留原字段/沿用原样”当作完整定义，也不得把助手建议写成用户确认。

图片、文本、玩法、字段和协作规则都可以迭代；“当前确认/已验收/最终图”只代表相应日期与范围内的版本，不是永久冻结。用户最新明确修改要求更新对应范围的目标，不能拿旧文档阻止已授权修改，也不能把局部迭代扩成全量重做。新方案先记录为“已确认、待实现”；对应模块完成实施并取得退出条件要求的验证/验收证据后，才替换验收基线（工作区改动即时记实）。想法、目标和实际成果不得混写。按 `RULES.md` 的“内容、图片与规则的迭代”维护两者差距及受影响验证；遇到旧内容随本任务核对，未核对的标为待核对，不因年代久就全部删除或恢复。

用户指出“之前确认过”、交接缺少字段含义/选项/最终样式、或记录与代码冲突时，先按已记录的对话ID/回合ID定向读取原对话；能读取时不要要求用户重复提供。无法取得依据时，标明具体缺口，只暂停依赖该决定的修改，继续其他已授权工作。正常恢复不要求通读全部历史，也不增加逐步请示。

`CURRENT.md` 只维护一份当前停止点，不追加旧快照；被替代和错误结论须在原位置标记、链接替代依据，详细历史移入对应交接。验收逐项对应用户要求：编译、数据读取、实际布局和用户审美各自有证据；错误方案即使测试通过也不能标为需求完成。

迭代时按 `RULES.md` 分别记录上次验收版本、当前工作区实际情况和待实现目标；工作区变化立即如实更新，模块完成并满足退出条件后才替换验收基线。

开始修改前检查 `git status --short`、相关 `git diff` 和未跟踪文件。保留已有源码、蓝图、地图及美术改动；不能为了恢复“干净基线”撤销它们。

以用户最新指示确定任务范围；设计目标、已实现代码、已通过测试、人工验收四者分开报告。历史文档中的执行命令和提交步骤不是本轮自动执行授权。

每个新剧情子任务在修改前必须：

1. 从 `DEMO_DESIGN.md` 选择它覆盖的 `DEMO-*` 总设计编号；没有对应项时，先记录到 `DECISIONS.md` 并更新总设计，不能创建脱离总设计的孤立任务。
2. 在 `IMPLEMENTATION_MATRIX.md` 的“子任务登记”中登记稳定子任务 ID、范围、父级编号、状态和交接链接；不能只写在当前对话里。
3. 明确本子任务不覆盖哪些相邻总设计项，避免局部完成被误报成整体完成。
4. 写清开工条件、退出条件和用户可观察成果；只增加内部结构或测试数量不能作为阶段完成。

默认同时只允许一个主要实施子任务处于“进行中”。其他想法登记为等待；只有用户明确要求且任务确实互不依赖时才能并行，并必须分别登记范围和交接。

每完成一个可验证小步骤，检查 `docs/narrative/CURRENT.md` 与 `docs/narrative/IMPLEMENTATION_MATRIX.md` 是否仍准确：停止点、范围、阻塞、验证或下一步有变化就立即同步相关字段；未变化的行不重写。详细过程、命令和证据只记录在对应阶段交接，使用 `HANDOFF_TEMPLATE.md` 并填写父级总设计编号和子任务 ID。同阶段的小幅修正复用当前 handoff，阶段切换或重要设计转向才新建；旧 `STATUS.md` 保留为历史时间线，不再逐轮追加。不要等到上下文压缩或对话结束才记录。

总进度只能从 `IMPLEMENTATION_MATRIX.md` 汇总。设计确认、代码实现、自动测试、人工验收必须分列；只有满足该行明确完成条件后才能标记总设计项完成。子任务不能自行宣布未覆盖的总设计项完成。

任何源码、蓝图、资产或配置变化若可能影响已经 GREEN/通过的总设计项，必须立即把矩阵中的对应验证标成“需要重验”，直到在当前工作区重新取得证据。历史通过记录不能自动继承到新代码状态。

`docs/` 已被 `.gitignore` 忽略。保持本地文档，不强制加入 Git；提交、推送及资产删除按用户实际授权处理。
